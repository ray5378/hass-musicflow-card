# v2.8.24 — 投屏/群组歌词对时修复：用采样时间锚定进度，tick 按真实经过时间推进

> 反馈：HA 卡片播放音乐时，歌词和进度的时间似乎对不准（尤其投屏 / 群组）。
> 排查确认问题真实存在，根因在卡片的本地时钟，不在歌词文件本身。

## 根因一：只有 local 客户端会外推，设备型 peer 把 2s 前的采样当成「此刻」

卡片 `_projectStatusPosition()` 原来只认 `status.reportedAt`：

| peer 类型 | status 时间字段 | 旧行为 |
|---|---|---|
| local 客户端 | `reportedAt`（周期上报采样时刻） | 按 `position + (now - reportedAt)` 外推 ✅ |
| DLNA / AirPlay / Sendspin / 群组 | **只有 `updatedAt`**（服务端状态采样时刻） | 原样返回，把最多 2s 前的采样当作现在 ❌ |

于是每轮 2s 轮询，歌词时钟被拉回旧位置，表现为「滞后 1~3s + 周期性回跳」。

**修法**：`reportedAt` 优先，缺失时回退 `updatedAt`，仍然保留 30s 过期与时钟异常保护。

## 根因二：250ms tick 固定 `+0.25`，定时器一被延后就永久走慢

HA 平板 / 后台标签页的 `setInterval` 会被节流或延后。固定步长不补偿实际经过时间，
误差会累积，歌词越走越晚。

**修法**：记录上一帧 tick 的墙钟时刻，按 `(now - lastTickAt) / 1000` 推进，单帧最多补 2s；
每次 status 校准后重置 tick 锚点，避免把轮询间隔重复加一遍。

## 附带：后端 LRC `[offset:N]` 不再被丢弃

`parseLrc()` 过去把 `[offset:N]` 当普通元数据跳过，带 offset 的歌词整体偏移。
现在解析时统一应用（正值让歌词提前 N 毫秒，时间戳钳位到 0）。
